# Архитектура StarBank Recommendations Service

## Краткое описание

MVP рекомендательного сервиса банка, реализующий выдачу рекомендаций на основе правил. Система поддерживает два типа правил:
* **Динамические правила** — хранятся в БД, управляются менеджером, по ним собирается статистика.
* **Статические правила** — встроены в код (`StaticRules`), используются как fallback при недоступности БД.

Архитектура соответствует требованиям REQ‑001–004 и NFR‑003.

---

## Компоненты приложения

| Компонент | Назначение | Соответствие требованиям |
|---|---|---|
| `RecommendationController` | REST-эндпоинты для менеджера и пользователя | REQ‑001, REQ‑002, REQ‑004 |
| `RecommendationService` | Бизнес-логика: проверка условий, fallback, инкремент счётчиков | REQ‑003, NFR‑003 |
| `RuleRepository` | Доступ к данным правил и статистике через Spring Data JPA | REQ‑003 |
| `StaticRules` | Конфигурация статических правил в памяти | NFR‑003 (fallback) |
| `ConditionStep` (интерфейс) | Единый контракт для условий (статические и динамические) | REQ‑004 |
| `FixedStep` | Реализация условий для статических правил | NFR‑003 |
| `QueryStep` | Сущность БД для шагов динамических правил | REQ‑001 |

---

## Внешние системы и интеграции

* **PostgreSQL / H2** — хранение правил, шагов и счётчика `applyCount`. В dev используется H2 (in‑memory), в prod — PostgreSQL.
* **Swagger UI** — документация REST API. Доступен по `/swagger-ui.html`.
* **Telegram Bot** — канал доставки рекомендаций пользователю (интеграция на уровне бизнес‑логики).
* **Внешняя система мониторинга/кеша** — вызывает API для сброса кеша и сбора метрик.

## Алгоритм выдачи рекомендаций (REQ‑004 + NFR‑003)

1. **Запрос:** Пользователь вызывает `GET /api/recommendations/{userId}`.
2. **Получение списка правил:**
    * Сервис пытается получить активные правила из БД (`RuleRepository.findAllByIsActiveTrue()`).
    * При ошибке доступа к БД (`DataAccessException`) срабатывает fallback: используются только статические правила из `StaticRules.STATIC_RULES`.
3. **Проверка условий:**
    * Для каждого правила проверяются условия через интерфейс `ConditionStep`.
    * Динамические правила используют шаги из БД (`QueryStep`).
    * Статические правила используют шаги из `StaticRules.getStepsForRule()` (`FixedStep`).
4. **Оценка условий:** Метод `evaluateCondition` сравнивает атрибуты пользователя (возраст, доход) с условиями правила.
5. **Сбор статистики (REQ‑003):**
    * Если правило подошло и оно динамическое (имеет `id != null`), увеличивается счётчик `applyCount` и сохраняется в БД.
6. **Ответ:** Возвращается список `RecommendationDto` с подходящими продуктами.

### Ветвления алгоритма

- **Если БД доступна:** список правил = статические + динамические.
- **Если БД недоступна:** список правил = только статические. Сервис продолжает работать (NFR‑003).
- **Если правило не имеет условий:** оно считается выполненным (всегда применяется).

## Реализация требований

### Функциональные требования (REQ)

* **REQ‑001 (Создание правил):** Реализовано в `RecommendationService.createRule()` и `RuleController.post()`. Правила сохраняются в БД вместе с шагами.
* **REQ‑002/REQ‑003 (Статистика):** Реализовано через поле `applyCount` в сущности `Rule` и JPQL‑запрос в `RuleRepository.findActiveRulesWithStats()`. Эндпоинт `/api/rules/stats` отдаёт статистику.
* **REQ‑004 (Выдача рекомендаций):** Реализовано в `RecommendationService.getRecommendations()`. Учитываются оба типа правил, условия проверяются через единый интерфейс `ConditionStep`.

### Нефункциональные требования (NFR)

* **NFR‑003 (Отказоустойчивость):** Реализован fallback на статические правила при `DataAccessException`. Сервис не падает, а продолжает выдавать рекомендации.
* **Логирование:** В `RecommendationService` добавлены логи уровня `DEBUG` при формировании списка правил и `WARN` при недоступности БД.
* **Производительность:** Счётчик `applyCount` обновляется синхронно при выдаче рекомендаций. Для дальнейшего улучшения можно вынести инкремент в асинхронный поток или использовать кеш (Caffeine).

## Взаимодействие компонентов (по слоям)

**Слой контроллера:**
* Принимает HTTP‑запросы.
* Преобразует DTO → вызывает сервис.
* Возвращает HTTP‑ответы и коды состояния.

**Слой сервиса:**
* Содержит основную бизнес‑логику.
* Управляет стратегией получения правил (БД или fallback).
* Проверяет условия правил.
* Обновляет статистику.

**Слой доступа к данным:**
* Spring Data JPA + Hibernate.
* Liquibase для миграций БД.
* Репозитории работают с сущностями `Rule`, `QueryStep`.

**Конфигурация и память:**
* `StaticRules` хранит статические правила и их шаги в памяти.
* Не зависит от БД, загружается при старте приложения.

## Развёртывание и конфигурация

Для запуска в prod необходимо:
1. Подключить PostgreSQL через переменные среды (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`).
2. Убедиться, что Liquibase применил миграции (`master.changelog.xml`).
3. Отключить H2‑консоль (`spring.h2.console.enabled=false`).
4. Установить уровень логирования `INFO` для `com.starbank.recommendations`.

См. также: [Инструкция по развёртыванию](deployment.md).

## Расширяемость

Архитектура позволяет легко добавить:
* Новые типы условий правил — достаточно реализовать интерфейс `ConditionStep`.
* Новые каналы доставки (кроме Telegram) — добавить новый контроллер или сервис доставки.
* Асинхронное обновление статистики — вынести инкремент `applyCount` в отдельный поток или очередь.
